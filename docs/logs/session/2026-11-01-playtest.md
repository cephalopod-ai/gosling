## Findings

### PT-20261101-01-F01 — Fresh unconfigured Settings reports an unknown provider

- **Classification:** confirmed observed UX defect; **severity:** Low;
  **scenario:** LC-02, `docs/test_scenarios/01-first-run-and-lifecycle.md`.
- **Steps:** Start Desktop with a fresh disposable backend root and no provider
  credentials. Open Settings. Return from Configure providers to Settings, or
  stop and relaunch and open Settings again.
- **Expected:** The normal unconfigured state should identify the need to choose
  a provider and direct the user to setup.
- **Actual:** Models displays two notifications titled `Provider name lookup`
  with `Unknown provider in config -- please inspect your config.yaml`.
  It recurred after returning to Settings and after relaunch. The Configure
  providers button did open the provider list. In the same empty state a chat
  submission correctly reported `No AI provider is configured` and retained its
  draft, and CLI `doctor` identified no provider and suggested configure.
- **Impact:** A new user is directed to inspect a configuration file for a
  routine missing-setup state and receives duplicate notices. This does not
  establish that a configured unknown provider behaves incorrectly.
- **Evidence:** Visible accessibility-tree text, reproduced on two launches;
  no screenshot retained. Desktop backend revision unknown as above.
- **Suggested follow-up:** Distinguish no selection from an invalid configured
  provider and deduplicate notices. Retest with a fresh root, then separately
  test a deliberately invalid configured provider on a freshly built Desktop.

### PT-20261101-01-O01 — Cold development launch required Reload once

- **Classification:** observed once, environment-dependent suspicion; **severity:**
  Note; **scenario:** LC-02 / Desktop first launch.
- **Steps:** After restoring the missing Electron binary, start the development
  GUI with the existing dependency tree and fresh isolated state.
- **Expected:** Reach the first screen without a renderer error.
- **Actual:** A `Honk!` error screen said `Failed to fetch dynamically imported
  module: http://localhost:5173/src/App.tsx`. The dev log immediately before it
  recorded Vite dependency optimization and reload. Clicking Reload reached the
  new-chat screen. A subsequent launch with the warmed dependency cache reached
  the screen without this error.
- **Impact:** A developer may need to recover manually during cold startup. The
  available evidence does not establish a packaged-app defect or a deterministic
  product bug. No screenshot or complete renderer log was retained.
- **Suggested follow-up:** Replay with a clean, controlled dependency cache and
  capture the full renderer/network logs; retest packaged Desktop separately.
